# support

Built 2026-11-08. **Support tickets**: a person asks Circaso for help from the app (SU1-SU4) or through Asha's `openSupportTicket` tool; staff work the tickets from the ops dashboard through `SupportDesk` (the ops module's routes, on the ops gateway only). Schema `support`, Redis prefix `sup:`, no stream (publishes nothing; reads `events:identity`), frames module `support`.

## Overview

### Owns
- Tickets: subject, description, category, status, source (`APP` or `ASHA`), the one payment or chat it is about (ids only), the assignee (a staff id from ops, never an email), whose turn it is (`waiting_on`), and the number shown as `CS-000123` (a database identity).
- A ticket's messages: the user's replies, staff replies and staff-only internal notes.
- The `support` realtime frames, kept 7 days for replay.

### Contract (`support:api`)
- `SupportTickets.open(NewTicket)` → `OpenedTicket(ticketId, number)`: Asha's tool. The same use case as SU1, so the same rules and the same daily cap.
- `SupportDesk`: `queue(filter, cursor, limit)`, `ticket`, `ofUser`, `reply`, `note`, `assign`, `changeStatus`, `counts`. Who may call what (SUPPORT, ADMIN) and the audit line are the ops module's.
- `TicketId`, `TicketNumbers.format`, the enums, `SupportFrames`, `TicketRepliedFrame`, `TicketUpdatedFrame`.

### Integrations used
- None. The push for a reply is the gateway's (`GatewayRealtime.pushFor`).

### Depends on
- `wallet:api` `Wallets.transfer`: a ticket's `transferId` must be one the user sent, received or signed (`senderId`, `recipientId`, `signerId`).
- `messaging:api` `ChatDirectory.isMember`: a ticket's `chatId` must be a chat the user is in.
- `identity:api` events: `AccountDeleted` deletes the user's tickets (their messages by the foreign key). Not `AccountStatusChanged` to `DELETED`: while the account can still be restored, support may be what restores it.

## Data

```sql
CREATE TABLE support.tickets (
    ticket_id uuid PRIMARY KEY,            -- UUIDv7 from OrderedIds; created_at is the instant inside it
    number bigint GENERATED BY DEFAULT AS IDENTITY UNIQUE,
    user_id uuid NOT NULL, subject text, description text, category text, status text, source text,
    context_transfer_id uuid, context_chat_id uuid, assignee_id uuid, waiting_on text,
    created_at timestamptz, updated_at timestamptz, last_message_at timestamptz, version bigint
);
CREATE INDEX tickets_user_idx ON support.tickets (user_id, ticket_id);          -- SU2, ofUser, account deletion
CREATE INDEX tickets_status_idx ON support.tickets (status, ticket_id);         -- queue by status; open and pending counts
CREATE INDEX tickets_assignee_idx ON support.tickets (assignee_id, ticket_id);  -- "mine"
CREATE INDEX tickets_category_idx ON support.tickets (category, ticket_id);     -- queue by category
CREATE INDEX tickets_unassigned_idx ON support.tickets (status, ticket_id) WHERE assignee_id IS NULL; -- unassigned
CREATE TABLE support.messages (message_id uuid PRIMARY KEY, ticket_id uuid REFERENCES support.tickets ON DELETE CASCADE,
    author text, staff_id uuid, body text, internal boolean, created_at timestamptz);
CREATE INDEX messages_ticket_idx ON support.messages (ticket_id, message_id);
CREATE TABLE support.realtime (...) PARTITION BY RANGE (sent_at);               -- as status.realtime, 7 days
```

- Because `created_at` is the instant in `ticket_id`, "created before" is `ticket_id < first UUIDv7 of that millisecond`, served by every queue index.
- Every change is one `UPDATE … SET …, version = version + 1 WHERE ticket_id = ? AND <condition> RETURNING *`; the ticket row is updated before its message is written, in one transaction; frames go after the commit.
- `last_message_at` moves with what the user can see (their replies and staff replies), never with a note.
- Redis: `sup:seq:{userId}` (frame `seq`, 8 days, renewed), `sup:opened:{userId}` (the daily cap, 24 h). No other keys.
- Job `support.purge-expired` (hourly): keeps the daily partitions of `support.realtime` (7 days). Tickets don't expire; they go with the account.

## Events

- Consumed: `events:identity` (group `support`): `identity.AccountDeleted` → delete the user's tickets. Idempotent.
- Published: none (`outbox = false`).
- Realtime (module `support`, replayed 7 days, `resync` past that):
  - `ticket.replied` `{ticketId, number, status}`: staff replied. Pushed when offline: "Circaso Support" / "We replied to your ticket CS-000123.", `kind: "support.ticket"`, `ticketId`. Never the text.
  - `ticket.updated` `{ticketId, number, status}`: staff changed the status. Not pushed.

## Error codes

| Code | Kind | When |
| --- | --- | --- |
| `support.ticket_not_found` | NOT_FOUND | no such ticket, or someone else's |
| `support.subject_invalid` | INVALID | subject not 3-120 characters |
| `support.description_invalid` | INVALID | description not 10-4,000 characters |
| `support.body_invalid` | INVALID | reply or note not 1-4,000 characters |
| `support.category_invalid` | INVALID | not a known category (SU1's mapper) |
| `support.status_invalid` | INVALID | `changeStatus` to `PENDING_USER` |
| `support.context_invalid` | INVALID | a transfer the user didn't send, receive or sign, or a chat they aren't in |
| `support.ticket_closed` | CONFLICT | a reply (user or staff) on a closed ticket |
| `support.rate_limited` | RATE_LIMITED | a sixth new ticket in the user's day; `retryAfterSeconds` |

## Asha

`openSupportTicket` (assistant `data/tools/SupportTools`): subject, summary, category, optional transferId and chatId; source `ASHA`; once per turn (`ToolContext.calledBefore`), whatever became of the first call; needs no agent token; label "Opening a support ticket…"; answers `{ticketNumber, status}` or a `{message}` the model passes on. The tool fits the subject (at a word, 120) and summary (4,000) to support's bounds itself. Its description and the prompt (`asha-2026-11-08-v1`) say: only after trying to help, always ask first and say what it will say, no secrets, tell the user the number.
